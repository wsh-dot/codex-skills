# 按提示词发现和阅读有用文件

## 如何判断“有用”

每个文件必须说明它支持哪项要求，或解决哪项待核事实。不能仅因为文件很多就全部加入。
先建立任务词表：业务对象、阶段/版本、关键约束、函数/表/API/规则/用例标识、用户点名的争议。
搜索从用户指定路径和当前目录开始，只有必要时扩大范围。跳过依赖、构建目录、秘密配置和无关备份。

文件名匹配只是发现候选。discover不读取正文，也不决定权威关系。
先看标题/版本/生效状态/目录，再定位相关章节；文件中引用的定义、边界和例外需要一起读。
不要仅搜索一个结论词就称为“核对完整”。

## 阅读顺序与用途

| 顺序 | 文件类型 | 要确定的内容 |
|---|---|---|
| 1 | 用户提示词、最新明确约束、适用工作区规则 | 产物、授权、禁止动作、已决定/未决定事项 |
| 2 | 用户指定的现行方案、规格、接入细则 | 业务合同、范围、完整前后置条件和来源优先关系 |
| 3 | 被引用的规则包、Schema、字典、接口协议 | 精确字段、规则条件、公式、约束及依赖 |
| 4 | 验收用例、反例、修订确认与冲突记录 | 预期、例外、版本变化和仍待决定的问题 |
| 5 | 当前代码、DDL、配置结构 | 仅支持“现在实现了什么”；不能自动推翻权威设计 |
| 6 | 真实原始样本、提取结果、运行凭据 | 身份映射、数字和例子是否真实；区分示意和实际运行 |
| 7 | 历史报告、旧版资料 | 解释历史变化；不能直接证明当前数据库或在线状态 |
| 8 | 待审稿及上轮问题 | 被审对象；不作为自身正确性的来源 |

这是查阅顺序，不是自动裁决冲突的权威排名。实际优先级必须从用户或文件中的明确规则确认。
草稿不是权威文件，不应作为authority加入sources；通过prepare --draft引入。

## 阅读深度

- 文档：先读版本和范围，再读目标章节及相邻条件/例外/引用条款。保留行号。
- 代码：用rg找入口、调用者、被调用方法和类型定义；避免只看函数名就断言职责。
- JSON：先解析结构，定位目标对象；同时读取作用域、条件、动作、目标、守卫、版本及依赖。
  数组中的位置、物理行号、业务ID是不同概念。
- 规则包：先manifest/版本和Schema，再读任务涉及的规则及必要依赖。没有读完整包时如实注明。
- 验收：读输入、前置条件、分支及预期，不把摘要伪装成逐字原文。
- 样本：核对原始内容与提取结果，区分文件位置、source_order和运行时ID。
- PDF/Word/图片：保留原始文档位置与提取定位。提取文本是派生证据，不能冒充原文全文。
- 大文件：先搜索，再读完整语义段；信息超出上下文时分段阅读并记录覆盖，不能静默截断。
- 缺失文件：搜索合理替代路径和明确版本；找不到则记录，不凭常识补出内容。

每个sources条目包含：绝对路径、角色、用途、版本依据、阅读顺序、实际行段。
ranges=[]表示完整纳入；有ranges则只能声明读取这些片段。
生成者必须读取reading-guide.md与source-bundle.md（可以分段），不能只看文件清单。

## 根据任务改变检查内容

- 实施讲解：范围、阶段、责任划分、调用链、错误状态、人工修订、事务、验收及来源冲突。
- 技术方案：约束、架构决策依据、接口、依赖、边界与风险；不要把建议写成已实施。
- 数据分析：字段口径、样本范围、计算、缺失值和结论支持度；不能套用工程事务规则。
- 文案：受众、品牌/产品事实、长度、语气和禁止表述；无外部事实时不强制寻找代码或数据库文件。

这些只是路由提示。最终criteria必须回指本次用户提示词，不能机械照抄分类清单。

## 涉及来源冲突时

依据本次任务定位现行规则、方案细则、用户确认、冲突记录与对应验收预期。核验版本及其生效关系；不能根据文件名日期自行确定优先级。

任务涉及关联基数冲突时，同时读取必要的规则、细则、用户确认、歧义记录与验收预期。记录双方来源，并检查公式、人工修改调用链、示例数字和结论有没有暗中选边。“单列不裁定”与“正文按某口径计算”互相矛盾，不能判为通过。

## 来源阅读完成门槛

冻结前由Antigravity核对：
1. 提示词每项要求均映射到criteria，没有仅凭模型记忆下结论的关键事实。
2. 每个criteria的source_ids覆盖必要来源；纯格式要求可以为空。
3. 已追踪必要引用，读取范围足以保留条件、例外和冲突。
4. 未取得的证据明确标记；不能混同“不存在”和“没有读取到”。
5. 明确sources只提供了哪些片段；生成与审查均使用同一份冻结内容。

若这一步不能完成，先补读；无法取得的关键证据应形成明确阻塞。不要启动注定靠猜测通过的循环。
